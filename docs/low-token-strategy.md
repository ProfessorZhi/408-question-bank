# 408 PDF → Markdown：低 Token 成本方案

> 适用范围：2009—2026 年真题 18 套 ×47题，以及 2027 模拟卷 1—4 共 188 题，总计 **1034 题**。
> GitHub Actions 额度已耗尽；所有校验在 FJPCOS 本地完成，不触发 CI 的重跑。
> **重要：原始逐页文本 ≠ 已完成的题目 Markdown，更不等于内容校对通过。**

## 成本结论

昂贵的是让云端大模型反复阅读全页图片、逐题重写答案和展开长链推理，不是从 PDF 复制文字。
采用 **PyMuPDF / 离线 OCR → 自动分题 → 差异检测 → 只针对疑点调用模型 → 人工校核关键题**。

- **本地文字层提取：0 模型 Token。** 既有 42 个 PDF 中，32 个具备文字层（仍需逐页判断）。
- **离线 OCR：0 模型 Token。** 当前缺文字层的 10 个 PDF 合计约 **89 页**：模拟卷 2—4 六个文件共55页，2019/2021/2024/2025 真题答案共34页。OCR 精度不足时，不准自动标为已校验。
- **结构检查/查重/答案映射/文件完整性/哈希校验：0 模型 Token。** 使用 Python。
- **模型预算留给难点**：识别质量差的公式、图表、长代码、关键计算题，多来源答案冲突。每次只发送相关题目及页图裁片，避免重复附送整个 PDF。
- 每年每卷每题的云模型 Token 使用量取决于选定的提供商、上下文长度、输出长度和图像计费方式，不应在未测量前编造具体金额。

## 新增脚本

`tools/batch_extract.py` 支持**逐页缓存**、来源哈希校验、有限页数运行和离线 OCR 按需调用。

在 FJPCOS 新仓库工作目录执行：

```powershell
# 已经有文字层的页面先快速提取，只进 staging，不写正式试题
python tools/batch_extract.py --scope all --ocr off --limit-pages 0

# 然后仅对无文本层/文本很短的页面走离线 OCR
# 每次12页可断点续跑；重复运行会复用相同参数的缓存
python tools/batch_extract.py --scope all --ocr auto --limit-pages 12

# 扫描件模拟卷可单独推进
python tools/batch_extract.py --scope mock --ocr auto --limit-pages 12
```

临时内容在 `build/_scratch/408-raw-pages/`（已被 .gitignore 忽略），逐页保存 .txt / .json，含 PDF 相对路径、页码、原文件 SHA-256、OCR 均值置信度、是否含图、`status: unverified`。如被中断，重新运行即可。

**注意**：当前缓存区不会自动生成 `questions.md` 与 `solutions.md`，所以不会错误抬高进度。后续需通过题号识别、选项与小题校对、原卷回看，将实际可靠的文本合并进正式文件。

## 分批验收

| 阶段 | 产物 | 准入 |
|---|---|---|
| A. PDF 入库 | 2026 试题+解析+sha256 | 文件真实存在且来源可追溯 |
| B. 批量预处理 | 全部 PDF 逐页 txt/json | 无丢页，OCR 失败单独记录 |
| C. 结构化 | 每卷 questions.md + solutions.md | 40选择+7综合、选项A-D、解析题号、图片引用 |
| D. 校验 | 逐题异议单和 proofread 状态 | 校验公式/图表/代码/计算、原卷页码可回溯 |

优先试点：**2025 真题一卷（文字层）＋模拟卷 2 一卷（扫描件）**。先测量真实错字率、OCR 失败率、模型调用次数和人工校对工时，再按相同流程推进剩余20套。

不要直接从无明确许可的第三方 Markdown 仓库整篇搬运；保留来源和权利说明，仓库始终为 Private。
